## 2. Como rodar (o que mudou)

1. **Sempre que alguém atualizar arquivos do projeto por fora do IntelliJ:** primeiro **File → Reload All from Disk**, depois, se o `pom.xml` mudou, **aba Maven → Reload All Maven Projects**. Na ordem inversa, o IntelliJ grava a versão antiga por cima (aconteceu duas vezes; seção 10).
2. Rode os testes (`src/test/java` → Run 'All Tests'). Esperado: **190**.
3. Rode o `Main`. O Flyway aplica sozinho as migrações novas (V3 troca de senha, V4 estoque mínimo).
4. **Opcional, para a apresentação:** pgAdmin → banco `caixa` → Query Tool → abra `scripts/dados_exemplo.sql` → F5. Cria 8 produtos (por unidade, kg e metro, com estoque mínimo; o cimento aparece em vermelho de propósito) e 2 clientes. Pode rodar de novo sem duplicar. Não é migração do Flyway de propósito: dado de demonstração não pode entrar sozinho no banco de uma loja de verdade.
5. **Dependência nova:** Ikonli 12.4.0 (ícones). O Maven baixa sozinho no passo 1.

## 3. Revisão geral: o que foi encontrado

| Problema | Gravidade | Correção | Prova |
|---|---|---|---|
| Se o banco caísse no meio de uma venda, o carrinho da tela ficava "finalizado" e travado; o operador teria de passar tudo de novo | **Alta** | `RegistrarVenda` não altera mais o carrinho que recebe: finaliza e grava uma **cópia** (`Venda.copiar()`) | Teste novo; sabotando a correção, ele reprova (teste de mutação) |
| Produto inativado com o carrinho aberto gerava "erro técnico" | Média | `ProdutoIndisponivelException`: mensagem de negócio na tela | Teste novo |
| Troco podia sair com fração de centavo (recebido "10,555") | Baixa | `PagamentoDinheiro` aceita no máximo 2 casas | Teste novo |
| Dois JavaDocs "órfãos" (`Venda`, `Operador`), desligados do método certo | Baixa | Reposicionados; uma varredura confirma que não há outros | — |

**Princípio que vale citar na apresentação:** um caso de uso **não deve modificar o objeto que recebeu da tela**. Se modificar e algo falhar no meio, a tela fica num estado que o banco não tem.

## 4. Nova interface

### 4.1 Barra de ferramentas

| Elemento | O quê | Por quê |
|---|---|---|
| Barra no topo | **Caixa · Produtos · Clientes · Relatórios · Operadores** (este só para administrador), com ícone e texto; a área atual fica em laranja | Num programa de caixa, o topo é ferramenta, não perfil |
| Menu do usuário (à direita) | Nome do operador ▾ → Trocar senha, Sair | Trocar senha é raro; não merece botão próprio. O nome fica visível porque o fechamento do caixa depende de quem está logado |
| Faixa de situação | "Caixa aberto por Ana em … · Gaveta: R$ …" | O estado do caixa sempre à vista, atualizado a cada venda |
| Áreas ainda não feitas | Mostram "esta área entra na próxima etapa" | Melhor que uma tela falsa |

**Ícones:** biblioteca **Ikonli**, pacote Material Design 2. Só a classe `Icones` conhece a biblioteca; as telas pedem "o ícone de produtos". Trocar de biblioteca = mudar uma classe. Os ícones são pedidos pelas constantes do `enum` da biblioteca, conferidas no próprio `.jar`: um nome errado vira erro de compilação, não ícone em branco na apresentação.

### 4.2 Caixa unificado

Antes eram dois botões, "Vender" e "Caixa". Em português, "caixa" quer dizer as duas coisas, e isso confundia. Agora:

- **Caixa fechado:** a própria tela pede o troco e abre.
- **Caixa aberto:** cai direto no PDV.
- **Gaveta (F10 ou botão no painel da direita):** dinheiro esperado na gaveta, recebido por forma de pagamento, **suprimento, sangria e fechamento**. Não deixa fechar o caixa com uma venda pela metade.

**Para a apresentação:** a tela mudou inteira e **nenhum caso de uso nem teste mudou**. É a prova prática de que a regra está separada da tela.

## 5. PDV

### 5.1 Teclado

| Tecla | Ação |
|---|---|
| Código + **Enter** | Inclui o produto (leitor de código de barras, código ou nome) |
| **F1** | Ajuda (lista de atalhos) |
| **F2** | Quantidade antes de passar o próximo produto (ex.: 2,5 kg) |
| **F3** | Buscar produto pelo nome |
| **F4** | Cliente (obrigatório para fiado; mostra só o nome, nunca o CPF) |
| **F5** | Preço do item selecionado (abaixo do custo só administrador) |
| **F6** | Quantidade do item selecionado |
| **↑ / ↓** | Seleciona o item, mesmo com o cursor no campo de código |
| **Delete** | Remove o item (só com o campo de código vazio; com texto, apaga a letra) |
| **F8** | Cancela a venda |
| **F9** | Pagamento: **1** Dinheiro · **2** Pix · **3** Crédito · **4** Débito · **5** Fiado · Enter confirma · Esc volta |
| **F10** | Gaveta |

**Onde mudar uma tecla:** só no `enum AtalhoPdv`. A barra do rodapé e a ajuda do F1 são geradas a partir dele.

### 5.2 Decisões que vocês precisam saber defender

- **O carrinho é um objeto `Venda` em memória.** Incluir, alterar e remover chamam métodos da `Venda`, que aplica as regras na hora. Só a busca de produto e a conclusão da venda vão ao banco, em segundo plano.
- **O campo de código nunca fica desabilitado.** O leitor de código de barras manda o próximo código em milissegundos; num campo desabilitado os dígitos se perderiam.
- **O carrinho sobrevive a uma ida a Produtos e volta.** O `Navegador` guarda o PDV durante a sessão e só o descarta no "Sair".
- **A prévia do troco** no pagamento é só para o operador separar as notas. O valor oficial vem do comprovante, calculado por `PagamentoDinheiro`.

## 6. Cadastro de produtos

### 6.1 O que dá para fazer

| Ação | Tecla | Regra (quem garante) |
|---|---|---|
| Buscar | **F3** | Enquanto digita, com pausa de 0,3 s para não ir ao banco a cada letra |
| Novo | **F2** | Código e código de barras únicos; preços válidos (`CadastrarProduto`) |
| Editar | **Enter** / duplo clique | Mesmas regras (`AtualizarProduto`); a **unidade não muda** depois do cadastro |
| Ajustar estoque | **F6** | Entrada, perda ou correção; Alt+E / Alt+P / Alt+C escolhem o tipo (`AjustarEstoque`) |
| Inativar / Reativar | **F7** | Inativo some do PDV mas fica no histórico (`InativarProduto`, `ReativarProduto`) |
| Excluir | **Delete** | Só apaga se nunca foi vendido; senão, inativa (`ExcluirProduto`) |

Na lista, **vermelho** = no estoque mínimo ou abaixo; **cinza** = fora de linha. Se uma regra recusar o cadastro, a mensagem aparece **dentro da janela** e o que foi digitado não se perde.

### 6.2 Novidades por baixo

- **Estoque mínimo por produto** (migração V4, `Produto.definirEstoqueMinimo()`, `Produto.precisaRepor()`). É por produto porque 5 parafusos é nada e 5 sacos de cimento é bastante. Segue o fracionamento da unidade: não existe mínimo de 2,5 martelos.
- **Excluir × inativar:** produto já vendido **não pode** ser apagado: as vendas antigas apontam para ele, e o próprio banco recusaria (chave estrangeira). O comportamento é igual ao da exclusão de clientes, que já existia.
- **Motivo do ajuste agora é opcional** (decisão do grupo). Ressalva registrada: o buraco maior de auditoria é que o sistema não guarda **quem** fez o ajuste; fica como melhoria.

## 10. Problemas de ambiente (para o grupo não repetir)

| O que aconteceu | Causa | Como evitar |
|---|---|---|
| Alteração "sumiu" (`Cliente.java`, depois `pom.xml`) | O IntelliJ grava por cima a versão que tinha aberta | **Reload All from Disk** antes de mexer, sempre que os arquivos forem atualizados por fora |
| Biblioteca de ícones não baixou | Mesmo motivo: o `pom.xml` foi sobrescrito | Idem; conferir que o `pom.xml` tem a linha `ikonli` |
| Na sincronização, arquivos quase ficaram para trás | O envio escolhia arquivos pela data de modificação, que nesta pasta nem sempre é atualizada | Agora a comparação é pelo **conteúdo** de cada arquivo (178 arquivos idênticos na última conferência) |
| `git commit` com erros de "pathspec" | Duas aspas simples (`''`) no PowerShell = texto vazio | Usar **aspas duplas**: `git commit -m "mensagem"` |
| "Author identity unknown" | Git sem nome/e-mail configurado | `git config --global user.name` / `user.email`, com o e-mail do GitHub |

## 12. Perguntas para estudar

1. Por que o `RegistrarVenda` grava uma **cópia** do carrinho? O que acontecia antes se o banco caísse no meio?
2. Por que um produto já vendido não pode ser apagado? O que o banco faria se o código tentasse?
3. Se a loja quiser que o pagamento seja no F12 e não no F9, que arquivo muda? E a legenda do rodapé?
4. Por que o estoque mínimo é por produto, e não um número fixo para a loja inteira?
5. Por que a unidade de um produto não pode mudar depois do cadastro?
6. Por que o campo de código do PDV não é desabilitado enquanto o produto é buscado no banco?
7. A tela de caixa mudou inteira nesta etapa. Quantos casos de uso e testes mudaram por causa disso? O que isso prova sobre a arquitetura?
8. Por que só a classe `Icones` conhece a biblioteca de ícones?
9. Qual é a diferença entre `ConsultarProdutos` (PDV) e `ListarProdutos` (cadastro)? Por que não usar um só?
10. Por que o orçamento não pode reaproveitar as regras do carrinho de venda (`Venda`)? (Dica: estoque e o princípio de Liskov.)
