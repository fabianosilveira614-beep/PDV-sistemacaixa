## 2. Como rodar na sua máquina

### Pré-requisitos

- **JDK 21 ou superior** e **IntelliJ IDEA** (já traz o Maven embutido).
- **Servidor PostgreSQL 16 ou superior.** Atenção: o **pgAdmin não é o banco**, é só um programa para visualizar. Para conferir se você tem o servidor, abra o pgAdmin: se em *Servers* aparecer "PostgreSQL 16/17/18" e ele conectar, está tudo certo. Se não, instale em <https://www.postgresql.org/download/windows/> (o instalador traz o servidor e o pgAdmin juntos; anote a senha do usuário `postgres` e mantenha a porta 5432).

### Passo 1 — criar usuário e banco do projeto (uma única vez)

No pgAdmin: clique no banco **postgres** → **Tools → Query Tool**. Execute **um comando de cada vez**: selecione a linha e aperte **F5**.

```sql
CREATE USER caixa WITH PASSWORD 'caixa';
```

```sql
CREATE DATABASE caixa OWNER caixa;
```

> Se executar os dois juntos, aparece `CREATE DATABASE cannot run inside a transaction block`. O pgAdmin envia tudo como um bloco único, e o PostgreSQL não permite criar banco dentro de transação. Basta rodar separado.

**Por que um usuário só para o projeto?** O `postgres` é superusuário e manda em todos os bancos da máquina. A aplicação deve ter só a permissão de que precisa: o `caixa` só manda no banco `caixa`. É o princípio do menor privilégio.

Se o seu PostgreSQL estiver em outra porta (veja no pgAdmin: botão direito no servidor → *Properties → Connection*), altere a primeira linha de `src/main/resources/config.properties`.

### Passo 2 — abrir e rodar

1. IntelliJ → **File → Open** → pasta `caixa-ferragem`. Ele reconhece o `pom.xml` e baixa as dependências sozinho.
2. Execute a classe `br.com.ferragem.Main`.
3. **Esperado:** janela com faixa verde e a mensagem *"Banco de dados conectado. Migrações aplicadas agora: 1."* Na segunda execução: *"Banco de dados conectado e atualizado."* (o Flyway não reaplica o script).
4. Testes: botão direito em `src/test/java` → **Run 'All Tests'**. Devem passar os 41.

### Problemas comuns

| Sintoma | Causa | Solução |
|---|---|---|
| Tela vermelha, "Causa: Connection … refused" | Não há PostgreSQL rodando nessa porta | Instale ou inicie o servidor; confira a porta |
| "Causa: password authentication failed for user caixa" | Usuário `caixa` não criado ou senha diferente | Passo 1 |
| "Causa: database caixa does not exist" | Faltou o `CREATE DATABASE` | Passo 1 |
| Linhas vermelhas `WARNING: sun.misc.Unsafe…` no console | Aviso interno do JavaFX 21 em JDKs novos | Pode ignorar, não é erro |
| Linhas vermelhas `INFO: Migrating schema…` | O Flyway escreve na saída de erro e o IntelliJ pinta de vermelho | Pode ignorar, é sucesso |

## 4. Fase 0 — a base executável

### O que acontece quando se aperta Run

1. **`Main.main()`** manda o JavaFX abrir a aplicação.
2. O JavaFX cria a **`AplicacaoJavaFX`** e chama o `init()`, que monta as dependências via `ConfiguracaoAplicacao.criarPadrao()`.
3. **`ConfiguracaoAplicacao`** lê a configuração (`ConfiguracaoBanco`) e cria o `FabricaConexao` e o `MigradorBanco`.
4. **`ConfiguracaoBanco`** lê o `config.properties`; variáveis de ambiente (`CAIXA_DB_URL`, `CAIXA_DB_USUARIO`, `CAIXA_DB_SENHA`) têm prioridade.
5. O JavaFX chama o `start()`, que desenha a janela.
6. O `start()` cria uma **`Task`** (tarefa em segundo plano) que chama `MigradorBanco.migrar()`.
7. O **Flyway** conecta no PostgreSQL, aplica o `V1__criar_tabelas.sql` se ainda não rodou e registra isso na tabela `flyway_schema_history`.
8. A janela mostra o resultado: verde (sucesso) ou vermelho, com a **causa raiz** do erro.

### Arquivos de projeto

| Arquivo | Função |
|---|---|
| `pom.xml` | Bibliotecas e versões: JavaFX 21.0.8, driver PostgreSQL 42.7.12, Flyway 12.6.0, JUnit 5.14.4. Java 21. |
| `config.properties` | URL, usuário e senha do banco, fora do código. |
| `V1__criar_tabelas.sql` | Cria as 10 tabelas. Comentários `-- RNxx` marcam as regras reforçadas pelo banco (fiado exige cliente, um caixa aberto por vez, estoque não negativo, pagamento ≤ débito…). **Nunca editar depois de aplicado**: o Flyway guarda um checksum do arquivo. Mudança no banco = novo arquivo `V2__descricao.sql`. |
| `tema.css` | Paleta e fontes num só lugar (critério 6 da rubrica). |
| `docker-compose.yml` | PostgreSQL via Docker, para quem preferir. |
| `.gitignore` | Ignora `target/`, `.idea/` e `.env`. |

### Classes da fase 0

- **`Main`:** só chama `Application.launch`. Existe separada porque o Java recusa iniciar quando a classe do `main` estende `Application` num projeto sem módulos (erro "JavaFX runtime components are missing").
- **`ConfiguracaoBanco`:** atributos `private final`; o construtor valida e lança erro claro se faltar algo; `toString()` esconde a senha. O método `carregar(Properties, Map)` **recebe o ambiente como parâmetro** em vez de ler `System.getenv()`, para que possa ser testado. É a ideia de inversão de dependência em pequena escala.
- **`FabricaConexao`:** único lugar que sabe abrir conexão (`DriverManager.getConnection`). Os repositórios da fase 3 vão usá-la.
- **`MigradorBanco`:** configura e executa o Flyway; converte `FlywayException` em `PersistenciaException`, **preservando o erro original como causa**.
- **`PersistenciaException`:** erro técnico, **não verificado** (`RuntimeException`), porque o usuário não tem como corrigir um banco fora do ar.
- **`ConfiguracaoAplicacao`:** *composition root*. O único lugar que dá `new` em classes de infraestrutura e entrega tudo pronto. É onde as dependências são injetadas.
- **`AplicacaoJavaFX`:** a janela. O acesso ao banco roda numa `Task` (outra thread) para a janela não congelar (critério 8 da rubrica). Erros de configuração não derrubam o programa: aparecem na tela, e o erro completo vai para o log.

## 5. Fase 1a — Produto e os 4 pilares da POO

### Regras implementadas

| Regra | Onde | O que garante |
|---|---|---|
| RN02 — margem | `Produto.calcularMargem()` | (venda − custo) ÷ venda × 100, 2 casas, HALF_UP. Calculada a cada chamada, nunca guardada, então nunca fica desatualizada. Custo 6,00 e venda 10,00 → 40,00%. |
| RN04 — estoque | `Produto.baixarEstoque()` | Não retira mais do que existe. Se recusar, **nada muda**. |
| RN06 — quantidade por tipo | `validarQuantidade()` + `verificarFracionamento()` em cada subclasse | Unidade: só inteiros (1,5 parafuso é recusado). Kg: até 3 casas (0,250 kg = 250 g). Metro: até 2 casas (1,35 m). Todos: maior que zero. |
| RN15 — preços | `Produto.alterarPrecos()` | Custo ≥ 0; venda > 0; no máximo 2 casas decimais. |
| Obrigatórios | `alterarIdentificacao()` | Código e nome não podem ser vazios. |
| RN12 — exclusão lógica | `Produto.inativar()` | Produto sai de linha, mas continua existindo para o histórico. |

### Os 4 pilares

| Pilar | Onde está | Como explicar |
|---|---|---|
| **Abstração** | `abstract class Produto`, `abstract class RegraNegocioException` | Não existe produto "sem unidade" na loja, então `new Produto(...)` nem compila. Também não existe "erro de regra genérico". |
| **Herança** | `ProdutoKg extends Produto` com `super(...)`; exceções herdam de `RegraNegocioException` | As subclasses reaproveitam toda a validação de código, nome e preços do construtor da classe mãe. |
| **Polimorfismo** | `validarQuantidade()` chama `verificarFracionamento()`, que cada subclasse sobrescreve | O mesmo código responde diferente conforme o tipo real. O `ProdutoContratoTest` roda os mesmos testes nos três tipos tratando todos como `Produto`. |
| **Encapsulamento** | Atributos `private`, **nenhum setter** | Estoque só muda por `baixarEstoque()`/`reporEstoque()`; preços só por `alterarPrecos()`. Tudo é validado antes de alterar. |

### Decisões de projeto (saber defender)

1. **Métodos `final` na classe mãe** (`baixarEstoque`, `validarQuantidade`, `calcularMargem`, `alterarPrecos`…). Nenhuma subclasse pode enfraquecer as regras comuns; só o fracionamento é customizável. Isso garante a substituição de Liskov (o "L" do SOLID).
2. **Produto nasce com estoque zero; o estoque entra por `reporEstoque()`.** A primeira versão recebia o estoque no construtor, e o compilador avisou (`this-escape`): o construtor da mãe chamava um método da filha antes de ela estar pronta. A correção também deixou o modelo mais fiel à loja, porque cadastrar e receber mercadoria são eventos diferentes. Na fase 2, o cadastro com estoque inicial vai gerar um `MovimentoEstoque` de entrada.
3. **`BigDecimal` para dinheiro e quantidade**, nunca `double`: `0.1 + 0.2` em `double` não dá exatamente `0.3`, e num caixa isso vira diferença de centavos. Para comparar, use `compareTo`, não `equals` (para `equals`, `3` e `3.000` são diferentes).
4. **Exceções de negócio verificadas** (estendem `Exception`): o compilador obriga quem chama a tratar. A tela vai capturar `RegraNegocioException` e mostrar a mensagem, que já vem pronta para o usuário.
5. **`Optional`** em `getId()` e `getCodigoBarras()`: deixa explícito que o valor pode não existir, em vez de devolver `null`.

### Pergunta difícil que o professor pode fazer

> "As três subclasses só diferem no número de casas decimais. Um `enum` não bastaria?"

É uma crítica legítima. Respostas defensáveis:
- Cada tipo tem regra **e** mensagem de erro próprias, e pode ganhar comportamento novo sem afetar os outros (ex.: venda mínima a granel).
- Um tipo novo (`ProdutoLitro`) entra **sem alterar** nenhuma classe existente. É o princípio aberto/fechado (o "O" do SOLID).

**Não responder** "usei herança porque o trabalho pedia": o enunciado avisa que forçar herança perde ponto.

| Conceito | Onde |

## 8. Correções feitas durante o caminho

| Problema encontrado | O que foi feito |
|---|---|
| A tela de erro escondia a causa real | Agora mostra a **causa raiz** (ex.: "Connection refused") e grava o erro completo no log. Clean Code: "tratamento de erros que preserve informações úteis". |

## 9. Perguntas para estudar (o professor pode fazer)

1. Se apagarmos o `Main` e rodarmos a `AplicacaoJavaFX` direto, o que acontece? Por quê?
2. Por que `ConfiguracaoBanco.carregar()` recebe um `Map` em vez de ler `System.getenv()`?
3. Qual a diferença entre `PersistenciaException` e `RegraNegocioException`? Por que uma é verificada e a outra não?
4. O que aconteceria com a janela se o banco fosse preparado direto no `start()`, sem a `Task`?
5. O que acontece se alguém editar o `V1__criar_tabelas.sql` depois de aplicado?
6. Por que `Produto` é abstrata? Dê um exemplo de polimorfismo no código.
7. Por que não existe `setQuantidadeEstoque()`?
8. Por que `baixarEstoque()` é `final`? O que poderia dar errado se uma subclasse pudesse sobrescrevê-lo?
9. Por que usamos `BigDecimal` e não `double`? Por que comparar com `compareTo`?
10. Onde a regra "não vender mais do que o estoque" está garantida? (Resposta: em `Produto.baixarEstoque()` **e** na constraint `CHECK (quantidade_estoque >= 0)` do banco, como defesa em profundidade.)
